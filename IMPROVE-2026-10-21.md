# Improvement Deep-Dive — 0xbridge — 2026-10-21

Scope: main. Sources read: `worker.js` (full), `README.md`, `lib/keys.js`, `schema.js`, `package.json`, directory listings (`handlers/`, `lib/`, `miniapp/`, `setup/`, `ui/`).

## Top recommendations (ranked, with effort S/M/L)

1. **Custodial key encryption-at-rest (M).** `schema.js` stores `users.nostr_priv` — hex private keys for every Telegram user — as **plaintext** in the Telegram Serverless SQLite DB. README's "never sent to the Worker" is true but incomplete: anyone/anything with DB read (platform compromise, dump, future logging mistake) gets every key. Design that fits the sandbox (no npm, V8):
   - **Envelope encryption with WebCrypto** (`crypto.subtle` AES-256-GCM — `crypto.getRandomValues` is already used in `lib/keys.js`, so WebCrypto exists in the sandbox; verify `crypto.subtle` availability on tgcloud before committing):
     - master key `BRIDGE_KEY_SECRET` set as a tgcloud env secret (never in code)
     - per-user random 96-bit IV; store `v1:<base64(iv||ct)>` in a new `nostr_priv_enc` column
     - HKDF/SHA-256 the master with the tgId as info string for per-user key separation (limits blast radius of any single-column leak)
   - **Lazy migration**: on first `/start` or `/post` after deploy, decrypt-if-plaintext → re-encrypt → null the plaintext column; log migration counts only.
   - **Key rotation**: version prefix (`v1:`) lets you re-wrap under a new master later.
   - **Strategic direction (already in README TODO)**: decustody — the Mini App generates and holds the key (NIP-07-style in-browser signing, or NIP-46 remote signer), the bot stores only the pubkey. Every custodial key is liability; the encryption above is the bridge, not the destination.
2. **Harden the bridge worker (S/M).** `worker.js` `POST /publish` is an unauthenticated, unrate-limited open proxy for arbitrary signed events to 4 major relays:
   - verify the event signature at the bridge (pure-JS schnorr already exists in `lib/` — port it, or bundle @noble/curves) and reject invalid events before touching relays (cheap DoS/reputation filter)
   - per-IP token bucket (CF Rate Limiting rules, or Workers KV) on `/publish` and `/query`
   - support NIP-42 AUTH for relays that require it (relay.snort.social and others increasingly do)
   - honor relay `OK` false results in the ack (currently `finish(true, 'sent')` fires after 1.5 s even without OK)
   - cap `/query` `limit` (unbounded today; parseInt of user input feeds the filter)
3. **Tests + pinning (S).** README claims the BIP-340 signer was "verified against vectors — 0/40 random-key failures" but no test file exists in the repo. Commit the vector test (official BIP-340 CSV + random-key round-trips) so future edits to `nostr_ec.js` BigInt math are gated. Pin `@tgcloud/cli` (currently `"latest"` — unpinned supply chain for a deploy tool with your bot token).

## Missing gates (CI/tests/protection)

- No CI, no tests, no lint. Minimal: a workflow running the BIP-340 vector test + `node --check` on all JS (the TG sandbox gives no second chances — a syntax error pushed via `tgcloud push` breaks the live bot). Add gitleaks (BOT_TOKEN handling is documented well; enforce it).

## Quick wins (code/config)

- `wsQuery` uses a flat 3.5 s timeout then closes all conns — close each socket on its own EOSE (already sends CLOSE) and resolve early when all relays EOSE'd; typical query finishes in <1 s.
- `worker.js` default relay list: relay.snort.social is effectively dead/redirected in 2026 — refresh defaults (e.g. add relay.nostr.band, relay.current.fyi or make RELAYS required env).
- `bech32Encode` in `lib/keys.js` is hand-rolled; it's only encoding (npub display) so risk is low, but add round-trip tests vs the vector test above.
- `handlers/message.js` `/post` — unreviewed here, but ensure it enforces per-user rate limits at the bot layer too (Telegram-side flood = bridge-side ban).
