# Security Audit — 0xbridge — 2026-10-20

## Summary

0xbridge is a Telegram ⇄ Nostr bridge: Telegram serverless handlers (`handlers/message.js`), a pure-JS Nostr event builder/Schnorr signer (`lib/nostr.js` + hand-rolled secp256k1 in `lib/nostr_ec.js`), and a stateless Cloudflare Worker (`worker.js`) that accepts signed events over HTTP and forwards them to public relays. It is a **custodial** bot: a fresh Nostr keypair is generated per Telegram user and the private key is stored **plaintext** in the bot's database (`users.nostrPriv`). The worker's publish endpoint has no authentication despite `wrangler.toml` documenting an optional `BRIDGE_TOKEN`. Light pass.

Findings: 0 Critical / 1 High / 2 Medium / 1 Low

## Findings

| ID | Severity | File/Area | Issue | Recommended fix |
|----|----------|-----------|-------|-----------------|
| BRG-01 | HIGH | `handlers/message.js` `ensureUser()` + schema | Per-user Nostr private keys stored plaintext in the Telegram bot DB (`nostrPriv`). Anyone with DB read access (hosting provider, SQL injection, leaked backup) owns every user's Nostr identity. The bot's own copy even says "Your keys live only in this bot's DB." | Encrypt at rest (per-user AEAD with an operator key), or better: make identities non-custodial (NIP-46 remote signing / user-held keys in the miniapp). At minimum, document the custodial risk honestly to users. |
| BRG-02 | MEDIUM | `lib/nostr_ec.js`, `lib/nostr.js` | Hand-rolled secp256k1 via BigInt (`ecMul` double-and-add, non-constant-time) and BIP-340 signing with default `AUX_RAND` = 32 zero bytes. Deterministic nonces are still safe per BIP-340, but zero aux removes fault-injection resistance and the custom EC math has no side-channel hardening — risky code to maintain for key handling. | Swap in `@noble/curves` (audited, constant-time) if the runtime allows; if pure-JS/no-deps is mandatory, add BIP-340 test-vector CI (partially present per comment) and use random aux. |
| BRG-03 | MEDIUM | `worker.js` + `wrangler.toml` | `/publish` accepts any well-formed signed event from anyone, with no rate limit and no token — `wrangler.toml` documents `BRIDGE_TOKEN` but `worker.js` never checks it. Open anonymous relay-publish proxy (spam vector against the listed relays; they absorb it, but your worker is the amplifier and may get rate-limited/abused). | Enforce `BRIDGE_TOKEN` (shared-secret header) when set, add a per-IP rate limit, and cap event size. |
| BRG-04 | LOW | `lib/nostr.js`, `handlers/message.js` | Hardcoded `RELAY_BRIDGE = https://0xbridge.workers.dev` and `MINIAPP_URL` placeholder shipped in source; deploy.sh notes tokens are env-only (good). | Move URLs to env/config. |

## Secrets Check

- Reviewed: `worker.js`, `wrangler.toml`, `deploy.sh` (env-var tokens via stdin — good), `lib/{keys,nostr,nostr_ec}.js`, `handlers/message.js`, `schema.js`, `package.json`.
- GHAS secret scanning unavailable; files read directly.
- **No committed secrets.** `deploy.sh` reads `TGCLOUD_TOKEN`/`BOT_TOKEN` from env only. Private keys exist only at runtime in the bot DB — which is exactly the problem in BRG-01.

## Dependency Notes

- `package.json` is minimal (455 bytes); runtime code is deliberately dependency-free (custom bech32 + EC). That removes supply-chain risk but concentrates correctness risk in `lib/nostr_ec.js` (see BRG-02).

## Fork/Upstream Freshness

Not a fork (original). HEAD 3bdd3a5.

## Recommended Actions

1. [HIGH] Stop storing plaintext private keys — encrypt at rest or go non-custodial (BRG-01).
2. [MEDIUM] Replace custom EC/Schnorr with `@noble/curves`; randomize aux rand (BRG-02).
3. [MEDIUM] Enforce `BRIDGE_TOKEN` + rate limit on `/publish` (BRG-03).
4. [LOW] Externalize hardcoded URLs (BRG-04).
